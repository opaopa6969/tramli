# なぜ tramli は効くのか —— アテンション・バジェット

ログイン・決済・承認などの処理で、一部分を直すために全体を読み直しているエンジニア向けの文書です。
tramli がデータの受け渡しをどう明示し、人間や LLM が確認する範囲をどう絞れるのか、どこにはテストやレビューが必要なのかを説明します。
tramli の予備知識は不要です。[English](why-tramli-works.md)

<a id="手続き型コードがバジェットに何をするか"></a>

## どんな痛みがあるか：小さな変更でも処理全体を追う必要がある

ログインが必要なページをユーザーが開いたとします。アプリは要求された URL を覚え、ログイン画面へ送り、セッションを作ってから元のページへ戻します。この受け渡しに抜けがあると、ユーザーは希望したページではなく既定のページに戻されます。

原因を調べるには、戻り先をどこで組み立てたか、ログイン要求をまたいで保持できたか、最後のリダイレクトがその値を使っているかを確認します。答えがハンドラ、フォーム、コールバックに散らばっていると、URL の組み立て方を少し変えるだけでも、呼び出し元や利用先まで追うことになります。

Cookie の設定やリクエストの URL スキームも確認が必要かもしれません。ただし、戻り先が渡されていない問題と、渡された URL の内容が間違っている問題では、必要な検査が違います。これらが一つの処理に混ざると、確認漏れが起きやすくなります。

この文書でいう**アテンション・バジェット**は、関係するコードを探し、依存関係を覚えておく負担を表す比喩です。人やモデルが理解できる行数に、決まった上限があるという意味ではありません。

## 普通のリファクタリングで解決できること

URL の組み立て、セッション作成、レスポンスの返却を関数に分け、引数と戻り値に型を付け、それぞれをテストする方法があります。短い一本道の処理なら、それで十分なこともあります。

難しくなるのは、途中で分岐したり、外部からの応答を待ったりする場合です。関数の型から一回の呼び出しに必要な入力はわかっても、「そこへ来るどの経路でも入力が揃うか」は別に確認しなければなりません。状態機械を使うと段階と経路を明示できます。tramli はさらにデータの入出力を宣言させ、経路をまたぐ依存関係を検査します。

<a id="tramli-がバジェットに何をするか"></a>

## tramli ではデータの受け渡しを明示する

tramli は Java・TypeScript・Rust 向けの制約付きフローエンジンです。状態は階層のない enum で表します。遷移は、自動で進む Auto、外部イベントを待つ External、条件で経路を選ぶ Branch の3種類です。`FlowDefinition` に経路をまとめ、1遷移分の処理を `StateProcessor` に書きます。その処理が読むデータを `requires`、提供するデータを `produces` で宣言します。

ログインの例では、次のように入出力を整理できます。これは契約を説明するための表記で、Java の構文ではありません。名前はアプリ側のデータを表しており、tramli に組み込まれた型ではありません。

```text
// LoginRedirectInit
requires: { RequestOrigin, AuthConfig }
produces: { LoginRedirect }

// SessionCreator
requires: { ResolvedUser, RequestOrigin, AuthConfig }
produces: { SessionCookie, FinalRedirect }
```

`RequestOrigin` は受信したリクエストの情報、`AuthConfig` はログインに関する設定です。`LoginRedirectInit` はそれらから、ログイン画面へ送るための `LoginRedirect` を用意します。`SessionCreator` は特定済みのユーザーとリクエスト情報、設定を受け取り、セッション Cookie と最終的な戻り先を作ります。

ここで気付けるのは、**`SessionCreator` が `LoginRedirect` を読むとは宣言していない**ことです。そこに保存された戻り先が必要なら、`requires` にその依存関係を追加する必要があります。tramli が業務上の要件から推測して補うことはありません。宣言されて初めて、手前の経路でその型が用意されるかを `build()` が検査できます。

実際の Java API を使ったコードは、[注文フローの例（英語）](article-build-time-dataflow.md#what-if-build-caught-it)で確認できます。

<a id="3つの保証"></a>

## ツールが検査することと、人が確認すること

`build()` は、フローの定義を組み立て、個々のフローを実行する前に検証するメソッドです。コンパイラの処理ではありません。CI で検査するには、テストから `build()` を呼ぶ必要があります。

| 確認したいこと | tramli が検査する範囲 | レビューやテストが必要な範囲 |
|---|---|---|
| この処理に必要なデータが届くか | `build()` が、フローの経路に沿って宣言上のデータの有無を検査する。 | 初期データを実際に渡し、実装が宣言を守る必要がある。メソッド本体から未宣言の読み取りを推測するわけではない。 |
| 遷移の構造に矛盾がないか | enum の名前の誤記はコンパイル時に検出される。Auto/Branch の循環や終端状態からの遷移などは `build()` が検査する。 | 宣言した遷移が業務上正しいかどうかは別に確認する。 |
| 図がフローの定義と一致するか | 定義から生成した Mermaid 図には、その定義が反映される。 | 保存した図は変更後に再生成する必要がある。Processor 内部の全処理を表す図ではない。 |

図の生成には次の Java API を使います。`authFlow` はアプリ側で用意したフロー定義です。

```java
String mermaid = MermaidGenerator.generate(authFlow);
```

[8項目の build() 検証](../README-ja.md#8項目-build-検証)が扱うのは、構造と宣言された依存関係です。戻り先 URL の値や Cookie の設定が正しいことまでは保証しません。そこはアプリの振る舞いとしてテストします。

<a id="読まなくてよかったものの原則"></a>

## 変更のために読む範囲をどう決めるか

セッション作成を直すなら、まず `FlowDefinition` と `SessionCreator` の契約、実装、テストを読みます。どこで実行され、前後の処理と何を受け渡すかを確認するためです。

入出力の意味を保った変更なら、この範囲でレビューできるかもしれません。`FinalRedirect` の意味を変えるなら利用先も確認します。`RequestOrigin` の解釈を変えるなら、その作成元や関係する設定も確認します。契約は依存先を探す手掛かりであって、Processor 同士が影響し合わなくなる仕組みではありません。

たとえば、1,800行のハンドラを50行のフロー定義と個別の Processor に分けたとします。定義と30行の Processor 一つなら、読み始める範囲は80行です。これは説明用の行数で、作業量の削減を測定した結果でも、残りのコードが無関係だという証明でもありません。どこから読み始め、どんな変更なら確認範囲を広げるかを判断しやすくすることが狙いです。

## LLM の作業にも役立つと考える理由

LLM に同じ変更を頼む場合も、フロー定義、関係する契約、対象の実装とテストを渡せます。依存関係が明示されていれば、散らばったコードから推測して組み立てる情報を減らせます。宣言の不足や構造の誤りには、`build()` のエラーという具体的なフィードバックも得られます。

これは作業を扱いやすくできると考える理由であって、モデルの正答率が一定量改善するという実証ではありません。人間の注意力と Transformer の attention は同じ仕組みではありません。標準的な Transformer の attention は重みを正規化しますが、そのことだけから「コードが増えると、重要な接続の重みが一様に薄まる」とは言えません。仕組みについては [Attention Is All You Need の §3.2](https://arxiv.org/html/1706.03762v7#S3.SS2)を参照してください。

ここでの主張は、**必要な入力、出力、経路を明示すれば、人間も LLM も探す範囲を絞れ、その分だけ見落としを減らしやすくなる**というものです。効果は作業内容、契約の書き方、実装に依存します。`build()` が通っただけで、生成されたコードが正しいと判断することはできません。

<a id="まとめ"></a>

## 変更時の確認手順

1. フロー定義から対象の処理と、そこへ到達する経路を確認する。
2. 契約、実装、テストを読み、受け渡すデータの意味が変わるなら作成元や利用先も確認する。
3. コンパイルと、`build()` を呼ぶテストで定義を検査し、変更した振る舞いや関係する外部連携をテストする。
4. 保存している図があれば、変更後の定義から再生成する。

段階をまたぐデータの受け渡しを追うことが、保守のたびに負担になっているなら、この方法が役立ちます。普通の関数呼び出しですでに依存関係が明確なら、フロー定義や契約を追加する手間の方が大きくなる場合もあります。
